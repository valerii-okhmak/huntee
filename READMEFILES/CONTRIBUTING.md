# Правила участі в проєкті 

- [English version](READMEFILES/eng/CONTRIBUTING.md)

Дякуємо, що хочете зробити внесок у наш проєкт!  
Щоб забезпечити злагоджену співпрацю, просимо дотримуватись наведених нижче правил та рекомендацій.

---

## Передумови

Перед початком роботи переконайтесь, що ви:
- Знайомі з основами Git і GitFlow
- Можете запускати проєкт локально і запускати тести
- Знайомі з правилами стилю коду
- Використовуєте останню стабільну версію Node.js і npm/yarn

## 1. Git-стратегія

Ми використовуємо **GitFlow** як основну модель роботи з гілками:

- `main` — стабільна продакшн-версія  
- `develop` — основна гілка для інтеграції змін  
- `feature/назва` — новий функціонал  
- `bugfix/назва` — виправлення помилок  
- `hotfix/назва` — термінове виправлення на продакшн  
- `docs/назва` — зміни лише у документації

### Іменування гілок

- Використовуйте нижній регістр і дефіси, наприклад: `feature/quiz-builder`, `bugfix/fix-login-error`
- Уникайте пробілів, спецсимволів та довгих назв


### Приклад створення гілки:

```bash
git checkout develop
git pull
git checkout -b feature/quiz-builder
```

## 2. Пул реквести (Pull Requests)

Після завершення роботи над фічею, створіть pull request **до гілки `develop`**, а не в `main`.

### Рев’ю PR

- Кожен pull request має бути перевірений щонайменше одним членом команди
- Перед мерджем PR повинен пройти всі тести та не містити конфліктів
- Обговорення по PR має відбуватись у коментарях, усі важливі рішення — документуватися

### Що має містити PR:
- Короткий опис реалізованих змін
- Посилання або назву задачі, до якої належать зміни
- Чітке пояснення, як ці зміни впливають на функціональність
- Позначення типу змін (новий функціонал, виправлення помилки, зміни в документації тощо)

### Перед створенням PR обов’язково:
- [ ] Перевірити код на синтаксичні помилки
- [ ] Переконатися, що всі тести проходять
- [ ] Перевірити відсутність конфліктів з `develop`
- [ ] За потреби оновити відповідну документацію

### Обов’язковий шаблон Pull Request

Будь ласка, використовуйте шаблон для опису змін (створити файл `.github/pull_request_template.md`), що має містити:

- Короткий опис змін
- Посилання на пов’язану задачу або issue
- Тип змін (feature, fix, docs тощо)
- Покрокові інструкції для перевірки (якщо потрібно)
- Скріни чи логи (за потреби)

> Зверніть увагу: ми очікуємо змістовні, добре структуровані пул реквести. Це пришвидшить їх перевірку і зменшить кількість доопрацювань.

## 3. Іменування комітів

Для зручності читання історії змін та автогенерації журналу змін (changelog), дотримуйтесь стандартизованого формату комітів:

### Формат:

Основні типи:
- `feat` — новий функціонал  
- `fix` — виправлення помилки  
- `docs` — зміни в документації  
- `style` — зміни у стилях (форматування, пропуски, крапки з комою тощо)  
- `refactor` — зміни у коді без зміни зовнішньої поведінки  
- `test` — додавання або зміна тестів  
- `chore` — службові зміни (оновлення залежностей, конфігураційні файли тощо)

### Приклади:
- feat: додано компонент тесту на soft skills
- fix: виправлено баг при відправці результатів
- docs: оновлено README з інструкцією запуску
- style: приведено CSS до єдиного стилю


> Коміт має бути коротким, інформативним і описувати суть змін.

## 4. Стиль коду

- **JavaScript/React**: Дотримуйтесь правил [ESLint](https://eslint.org/), щоб забезпечити узгодженість та чистоту коду.
- **CSS**: Можна використовувати звичайний CSS, CSS Modules або Tailwind CSS — обирайте той підхід, який найкраще підходить для вашої задачі та команди.
- **Іменування**: Використовуйте англійську мову для всіх назв змінних і компонентів. camelCase — для змінних, PascalCase — для компонентів.
- **Уникайте "магічних чисел"**: Замість незрозумілих числових значень використовуйте іменовані константи.
- **Додавайте коментарі за потреби**: Якщо логіка складна або неочевидна — залишайте короткі пояснення в коді.
- **Чистота та читабельність**: Пишіть код так, щоб його було легко прочитати, зрозуміти та підтримувати іншим учасникам команди.
